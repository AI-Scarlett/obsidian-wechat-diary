# 数据契约 v1 (data contract)

> ⚠️ **本文件是副本，权威版本在 `019Dairy/docs/data-contract.md`。**
>
> 任何修改必须**两边同时改**，否则 Python 版和插件版产出的日记会不兼容，
> 用户在两种形态之间迁移时格式就断层了。见 `00-decisions.md` D6。
>
> 上次与权威版同步：2026-08-05（对应 019 提交 `8febfd1`）

wechat-diary 只做一件事: 把微信消息写进你的 vault。本文件定义写入格式——
这是本项目与"任何管理这个库的 Agent"之间的接口, 破坏性变更会升版本号。

## 目录结构

```
<日记根目录>/
├── 2026/
│   ├── 2026-07-15.md      # 每天一个文件, 文件名 = 北京时间日期
│   └── ...
├── attachments/           # v1.1 起; 目前只有插件版(020)产出, 见规则 7
│   └── 2026/
│       └── 2026-07-15-2104-a3f1.jpg
└── _backup_v1/            # 仅 v1→v2 迁移时产生, 确认无误后可手动删除
```

**"日记根目录"在两种形态下的含义不同**（这是唯一的实现差异，结构本身一字不改）:

| 形态 | 日记根目录 |
|------|-----------|
| Python 版 (019) | `.env` 里的绝对路径 `DIARY_DIR` |
| 插件版 (020) | **vault 内的相对路径**，用户在插件设置里选（默认 `日记/`） |

插件版必须走相对路径 + `app.vault` API，才能被 Obsidian 正确索引、
触发链接更新、参与同步。见 `00-decisions.md` D4。

## 文件结构

```markdown
---
date: 2026-07-15
weekday: 周三
source: wechat-diary
---

# 2026-07-15

**21:04**

正文段落。同一分钟内的多条消息共享一个时间戳段头。

🎤 语音消息以 🎤 前缀标记 (文本为微信自动转写, 未配 AI key 时为转写原文)。

**21:10**

另一个时间点的段落。

---
_(今日封存于 23:02)_
```

## 规则 (对 Agent 的承诺)

1. **只追加**: 程序永不修改/删除历史段落 (用户主动「撤回」只删最后一条消息)
2. **原子写入**: 先写 .tmp 再 replace, 文件不会出现半截内容
3. **时间戳**: 所有日期/时间为北京时间 (Asia/Shanghai, 可经 TIMEZONE 配置)
4. **frontmatter**: 仅在文件创建时写入, 之后不再更新; 字段只增不改
5. **封存标记**: `_(今日封存于 HH:MM)_` 表示用户当天主动收尾, 可能不存在
6. **消息计数**: 一个 `\n\n` 分隔块为一条消息; 排除 `# ` / `**HH:MM**` /
   `---` / `_(` 开头的块
7. **图片 (v1.1 起, 020-only)**: 图片单独成块, 内容是一个 vault 全路径 wikilink
   `![[<日记根目录>/attachments/YYYY/YYYY-MM-DD-HHmm-xxxx.ext]]`。
   它按规则 6 计为一条消息, 「撤回」照常撤得掉。
   附件文件本身**永不删除**——撤回只删笔记里的引用, 留下孤儿附件由用户处置
   (规则 1「只追加」的延伸: 程序不删用户的原始素材)。

## 给管理此库的 Agent 的建议 (非约束)

- 回顾/检索/周报等在 vault 上直接做, 不要反向修改本程序的写入格式
- 需要给日记补充元数据时, 建议新增 frontmatter 字段而非改动已有字段

## 附: 插件版 (020) 的实现备注

以下不属于契约本身，只是记录插件形态下如何满足上面的规则。

- **规则 2「原子写入」**: Python 版靠 `写 .tmp → os.replace()`。插件版要用
  Obsidian 的 `vault.modify()` / `adapter.write()`，**这些 API 是否原子未确认**
  （调研中）。如果不原子，需要自己实现等价保护——否则崩溃时可能写出半截文件。
- **规则 3「时间戳用北京时间」**: 019 有 `config.now_bj()` 强制走时区，
  禁用裸 `datetime.now()`。TS 版同样要有一个统一入口，禁止直接 `new Date()`
  取日期——**文件名就是日期，这个不能错。**
- **规则 1「只追加」**: 插件版更要小心——Obsidian 里用户可能正好在编辑今天的
  日记文件。写入前要考虑和编辑器缓冲区的冲突（`vault.process()` 可能比
  `read` + `modify` 安全）。**待验证。**
- **规则 6「消息计数」**: 计数逻辑照搬 019 的 `count_messages`，注意排除
  `# ` / `**HH:MM**` / `---` / `_(` 开头的块。

## 契约 v1.1 — 图片附件 (2026-08-12)

**⚠️ 这是本副本先行、权威版(019)尚未同步的一条变更。** 按 D6, 019 侧必须跟着改文档,
否则契约两边不一致。具体状态:

- 019 (Python 版) **不产出**图片块 —— 它连 IMAGE item 都不解析, 行为不变, 老日记不受影响。
- 019 也**不需要能写**图片: 契约对它的要求只是「读到 `![[...]]` 块时当作一条普通消息,
  别当成坏数据去修」。它的 `count_messages` 本来就只按块首字符排除, 天然满足。
- 因此这是**向后兼容的增量**: 020 写的库 019 能继续追加, 反之亦然。
- 附件目录名 `attachments/` 与 Obsidian 默认附件目录同名但**不复用**用户的全局附件设置:
  日记的图必须跟日记一起备份/迁移, 挂在别处会在换库时断链。

## 插件版(020)实现注记 — 2026-08-11

- 规则 1 的「待验证」已解决: 写入统一走 `vault.process()`(原子读-改-写, 与编辑器缓冲区协调)。
- **与 019 的一处已知行为差异**: 当天文件已存在但内容为空(比如 Daily Notes /
  Templater 先建了空文件)时, 019 只追加正文段(不补 frontmatter), 020 会按新文件
  补全 frontmatter + 标题。020 的行为更合理, 应回灌 019 对齐; 在此之前, 该场景下
  两实现产出不逐字节一致。其余路径已逐字节对拍。

## 契约 v1.2 — 逻辑日: 凌晨 4 点前算前一天 (2026-08-16)

**"文件名 = 日期"里的"日期"自 v1.2 起指【逻辑日】**: 一天的边界不是零点,
而是凌晨 `dayStartHour` 点(默认 4, 020 在 data.json 可配, 无 UI)。
02:30 记的东西落在**前一天**的文件里, 段头时间戳仍写真实时间(`**02:30**`)。

- 动机: 备忘录/日记用户的"一天"到睡觉才结束, 夜猫子睡前的记录属于"今晚"。
  固定边界取代了 020 v0.3.0 前的滚动宽限期(30 分钟内续写算前一晚)——
  规则一句话讲得清, 且"凌晨 1 点新开一段"也不再落错天。
- frontmatter 的 `date`/`weekday` 与文件名同步, 都按逻辑日。
- 读取方(含 019 的 count_messages)无需任何改动: 文件内部结构一字未变。
- 019 (Python 版) 已于 2026-08-16 同步实现 (`DAY_START_HOUR` 环境变量, 默认 4),
  两实现同一深夜写进同一文件。
- 附带行为说明(0.3.0 单模式): 封存标记之后仍可能出现追加段——用户「结束」后
  又发消息时照记不误(规则 1"只追加"优先于封存行位置)。读取方不应假设
  封存行必在文件末尾。
