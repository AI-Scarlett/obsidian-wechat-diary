## A. 草案直接改(有明确更优解, 不需要谷雨决定)

**A1 · 共用模式下永远不删节标题 [DN-3, ENG-1] — §4.2 撤回 / §4.1 第一个匹配**
§4.1「文件里第一个匹配的标题行算数」意味着用户可以把 `## 微信随手记` 预先写进每日笔记模板来固定位置(Roy 这种"笔记有结构"的用户一定会这么做), 而 §4.2「撤到一条不剩 → 连标题一起删」删的就是模板里那一行; 下一条消息按「没有节 → 追加到文件末尾」, 位置从此错乱。发一条、撤回一次就触发, 且违反"不动用户自己的内容"。六个驳斥意见一致选方案 A。改法: 删掉 §4.2「连标题一起删」和「文件回到我们写入前的样子」两句, 改为「撤回只动节内内容, 标题留着」(与独立模式撤光后保留 `# 日期` 的现状同构, bindtest【29】已断言此行为); 封存行仍按 D9「空页不留封存行」清; fn 返回 "" 时 spliceSection 写成「标题行 + 单个换行」。§6 测试项「撤到空删标题」改成「撤到空只剩标题, 标题前后用户内容逐字节不变」; 契约 v1.4 加「节标题一旦存在插件不删」。设置项说明与 README 各加一句: 「想固定位置, 把 `## 微信随手记` 写进你的每日笔记模板, 标题下面留空」。

**A2 · 撤回/封存/计数不建文件、不建节 [ENG-3] — §4.2 _editDay / 跨天 _loadOrReset**
现有 undoLastBlock(3388)与 finalizeDay(3433)都是「文件不存在直接返回」, 而草案把四个操作统一进 _editDay 并无条件规定「没有节 → 把 fn("") 的结果作为新节正文追加在文件末尾」。finalizeDay 的 fn 对空内容原样返回(3441), undoLastBlock 找不到块也原样返回(3400): 昨天用户手写了一天没发微信, 今早第一条触发 _loadOrReset → finalizeDay(昨天) → 昨天的每日笔记末尾多出一个空的 `## 微信随手记`; 昨天连文件都没有时还会替昨天套模板建一篇。每隔几天就会发生一次。改法, §4.2 写死两条: ① `_editDay(day, fn, { create })`, 只有 _appendBlock 传 create=true; undo/finalize/countDay 在文件不存在或没有节时直接返回现状(empty / ok:false / 0), 不建文件不套模板; ② 共用模式下没有节且 fn("") 返回空串, 或 fn(body) 与 body 相同 → 不调 process、不落盘(也免得改 mtime 触发同步盘)。bindtest: 有用户内容无节的文件上跑三个操作 → 文件字节不变。

**A3 · 建文件一次 create; 模板已含同名标题时填进去而不是再追加; 插件建的文件写完复核; 空文件按"有文件无节" [DN-2, ENG-4] — §4.3**
三个具体点。① §4.3「以模板内容创建文件, 再追加我们那一节」没说是一次写还是两次写; 现有 _transform(3270–3285)本来就是一次 create, 两步反而倒退。② 模板本身含 `## 微信随手记`(A1 场景)时, "创建再追加"会产出两个同名标题, 第一条消息落在第二个标题下, 之后 §4.1 取第一个——第一条从此不计数、撤不到。③ Templater 的「新文件创建时触发」监听 vault create 事件不分创建者, 延迟约 300ms 后 read→modify 整篇写回; 单条消息的 create 落在 300ms 之内没事, 但用户连发时第 2/3 条在它 read→modify 窗口内追加就被写回的快照抹掉, 回执已说「记下来啦」——违反"发出去=记下了"; 模板里有 tp.system.prompt 之类慢命令时窗口是秒级。改法: `_createDayFile(day, body)` = 读模板 → renderTemplate → 在渲染结果上跑 locateSection: 有节则 spliceSection 填正文, 无节则末尾追加 → **一次** vault.create; create 抛「已存在」(TOCTOU)时改用共用模式的普通 splice fn 对现有内容 process, 模板只在 create 路径用、永不进 process。只在「本次由插件建了文件」这条路径上, create 后约 1.5s cachedRead 复核一次, 节里找不到刚写的块(按块原文比对)就再走一遍 _editDay 幂等补写; 不是每次写入都复核。文件存在但内容为空(Templater/Calendar 刚建的壳): 按「文件存在、无节」处理, 不套模板——壳是别人建的, Templater 马上会来填, 我们套模板只会和它撞; 独立模式对空文件补 frontmatter 的现状不动(零影响)。§4.3 明写这一句(驳斥者对此意见相反, 我取"不抢别人的壳", 与 A2 的"只在 create 路径套模板"一致)。bindtest: fakeVault 加 create 后异步 modify 覆盖的钩子模拟 Templater, 断言块被补回; 模板含同名标题 → 只有一个标题且消息在其下; create 第一次抛错 → 最终只有一个标题。README「诚实的限制」直说: 装了 Templater 新建触发器的, 插件建的当日文件会被它再处理一遍, 插件写完 1–2 秒复核补回。

**A4 · 转义只在共用模式做、挂在 _appendBlock、覆盖所有入口 [STD-1, ENG-8] — §4.2 转义 / §5 契约 / §6**
草案 §4.2 明写转义「扩到所有行、所有级别, 两种模式都生效」, 这与「对不开开关的用户零影响」直接冲突: 3319 现在只转义首行 `# `, 不开开关的老用户发一条两行消息「今天的安排\n## 计划」, 0.3.1 原样存、Obsidian 渲染成二级标题, 0.4.0 会存成 `\## 计划`——存盘字节变了, 与库里前 30 天风格不一致; 独立模式根本没有"节"的概念, 转义没有任何保护作用。第二个问题是挂点: writeAttachment 的 textAfter(3236–3240, 语音原声块与打字+语音混合条的文字部分)只做空行收敛不经过 write(), 转义若只挂 3319, 共用模式下第二行 `## x` 照样把节截断。改法: 转义只在 sharedDailyNote=开 时做, 挂在 _appendBlock(3287, write/writeAttachment/writeImage/appendLinkBlock 四条路的唯一汇合点)对整个 block 做; 独立模式 3319 一字不动。转义范围随 A6 的边界规则定为 `^#{1,6} `(行首加 `\`)。契约 v1.4 措辞改为「共用模式下写入方对节内 `^#{1,6} ` 行加 `\` 前缀; 独立模式规则不变(仅首行 `# `)」, 单独成句, 并给读取方加一句「行首 `\#` 视为原文 `#`; 旧文件与 019 产出不保证此规则」。bindtest 用例改成: 用 writeAttachment 发 textAfter 第二行 `## x` 的语音块, 断言节没被截断、n 正确。

**A5 · moment 令牌: 示例改带方括号, 校验改白名单, 桩要能暴露问题 [STD-2, ENG-5] — §2 校验 / §3 renderPath 与打桩**
真 moment 把未用 `[]` 括起的 A/a/s/e/h/m/d/D/M/Y/w/E/Q/l 等全当令牌。驳斥者实测: 草案自己的示例 `Assets/YYYY/MM` → `AM006t0/2026/08`, `attachments/YYYY` → `amttamc1206nt0/2026`, `daily/YYYY-MM-DD` → `6ami8/29/20262026/2026-08-29`(`l` 还带斜杠多出两层目录)。§2 的校验(四日期互异+非法字符)对这些全放行, 而 §3 让 bindtest 的桩「只认 YYYY/MM/DD/M/D、其余原样输出」, 恰好把这类错误藏起来——测试全绿线上落进乱码文件夹。另外四日期互异放过 `YYYY/MD`(01-12 与 11-02 都是 `2026/112`, 两天同文件)。改法: ① 草案/README/设置项说明的示例全改成 `[Assets]/YYYY/MM`, 说明写「英文字母会被当成日期代码, 文件夹名要放在方括号里, 与 Obsidian 每日笔记『日期格式』规则相同」; ② 校验改白名单: 剥掉 `[..]` 后剩余字母只允许 moment 日期令牌集合(YYYY/YY/M/MM/MMM/MMMM/D/DD/DDD/DDDD/d/dd/ddd/dddd/E/e/w/ww/Q), 时分秒与 AM/PM 令牌一律拒——这样「从每日笔记设置导入」带回的 `YYYY-MM-DD dddd` 之类合法格式不会被拒; ③ 互异检查改为渲染同一年 366 天 + 次年 1 月 1 日全部互不相同(只在校验时跑一次), 取代四个特例日期; ④ bindtest 桩必须实现 `[..]` 字面量, 并把白名单外的字母替换成可见占位(如 `?`), 让「Assets 不括起来」在测试里也失败。main.js 目前没 import moment, 这是全新引入的行为, 没有现成保护。

**A6 · locateSection/spliceSection 写成可直接编码的定义: 任意级别标题截断、围栏内不算、边界与换行归属写死 [DN-1, ENG-9, STD-9①] — §4.1 / §4.2**
三个洞。① §4.1「三级及更低不截断」的前提"用户在我们节里不会写"对每日笔记用户不成立——插件的节一旦被用户固定在文件中间(A1), 节后面就是用户的地盘; 用户在节后写 `### 备注` + 正文, 按草案落进节正文, isMessageBlock(3161–3168)只排除 `# `, 「撤回」删的就是用户那段, 与 §4.2「标题后面若有用户内容, 逐字节保留」自相矛盾。A4 保证插件永不写任何级别的标题行, 所以边界截止到下一个任意级别标题行不损失任何功能。② 用户每日笔记里我们的节后紧跟代码块(模板末尾固定放 dataview/shell), 块内 `# 注释` 被当终止标题: 围栏开头几行落在节内成为"最后一条消息", 「撤回」删掉用户的 ``` 行, 代码块从此不闭合。③ §4.1 只给了 `{start, end, bodyStart}` 三个字段名, 没定义 end 含不含标题前/节后的空行; 「节外逐字节不动」「节后隔一个空行」在用户留了三个空行时互斥; 「文件回到写入前的样子」在末尾换行上做不到(原文 `foo` / `foo\n` / `foo\n\n` 三种无法区分)——两个人会写出两种实现, §6「节外逐字节不变」的断言落不了笔。改法, §4.1 补精确定义: 逐行按 `\n` 扫描(标题行允许尾随空白含 `\r`), 维持 inFence 状态(遇 ``` 或 ~~~ 开头的行翻转), inFence 时既不匹配我们的标题也不当终止标题; 文件以 `---\n` 开头先跳到闭合 `---` 之后再扫。返回 `{ headingStart(标题行行首), bodyStart(标题行换行之后), bodyEnd(下一个 `^#{1,6} ` 行行首, 或文件长度) }`; 节的范围 = [headingStart, bodyEnd), 节后的空行归节内; fn 拿到 body 去掉尾部空行、末尾单个 `\n` 的版本; 写回 = 前段 + (前段非空且不以 `\n` 结尾则补 `\n`) + `\n` + 标题行 + `\n` + 新正文(rstrip 后补单个 `\n`) + (后面还有内容则再补一个 `\n`) + 后段。承诺改成可验证的一句: 「bodyEnd 之后的内容逐字节不动; 标题前允许多一个空行」。契约 v1.4「节的范围到下一个一/二级标题」改成「到下一个任意级别标题」。测试表: 「三级标题也截断」「节后紧跟含 `# ` 行的代码块」「节后三个空行再接用户标题」「三种文件结尾(无换行/一个/两个)各一条」。

**A7 · _editDay 返回值与 _appendBlock 空内容分支写死 [ENG-2] — §4.2 / §6**
write(3336)/writeAttachment(3238)/appendLinkBlock(3251)/writeImage(3380)四个调用点都是 `countMessages(finalContent)` + `finalContent.includes(CLOSING_MARKER)`, 而 _transform 返回全文; 草案只说「改走 _editDay」, 没说它返回节正文还是全文。照现有结构接上: Roy 的每日笔记上面有 20 个自己的段落, 第一条微信回执是「今天第 21 段」, 开页前缀永远不出现——「第 N 段」是送达确认信号(D9), 数错等于信任崩掉。另外 _appendBlock 的 existing 为空分支写 frontmatter + `# 日期`, 共用模式下 body 为 "" 时若不分叉, 用户文件里我们的标题下会多出一段 frontmatter。改法, §4.2 加一句: `_editDay(day, fn)` 返回 fn 所作用范围的最终文本(独立模式=全文, 共用模式=节正文), 四个调用点的段数与 sealed 只看这个返回值; _appendBlock 的 fn 在共用模式下 body 为 "" 时产出 `**HH:MM**\n\n块\n`(不带前导空行, 不带 frontmatter/`# 日期`, 首尾空行交给 spliceSection 收口)。bindtest: 文件里先有 3 段用户内容 + 用户标题, 再写第一条 → n===1 且回执带开页前缀。

**A8 · 共用模式节正文做 CRLF→LF 归一化 [DN-4, ENG-7] — §4.1 / §4.2**
独立模式文件全是插件写的, 永远 LF; 共用模式文件来自用户工具(Git for Windows 默认 autocrlf=true、Windows 编辑器、同步盘), CRLF 真实存在。驳斥者在真 DiaryWriter 上实测: CRLF 节正文 `**21:04**\r\n\r\n第一条\r\n\r\n第二条` 的 countMessages = 1(split("\n\n") 切不开, HEADER_FULL_RE 是无 m 标志的精确匹配排不掉整块), 「在吗」永远报 1 段, 「撤回」把整节一次删光, 回执预览只显示前 12 字, 用户以为只撤了一条。改法: 共用模式 _editDay 只对 locateSection 切出的节正文做 `\r\n`/`\r` → `\n` 再交给 fn, 写回节内用 LF(Obsidian 编辑器本身写 LF, 混合换行无害, 不必还原 CRLF), 节外字节一个不碰; 独立模式不动(零影响, 独立模式文件被 autocrlf 改过的隐患记停车场)。bindtest: 全 CRLF 用户文件 + CRLF 节正文, 写两条 → n===2, 撤回只删最后一条, 节外仍是 CRLF 逐字节不变。

**A9 · 零影响的证据要硬: 路径函数加默认值兜底, 桩补 moment, 加黄金文件回归 [STD-3] — §6 测试 / §2 默认值**
草案 §6 拿「现有 405 断言不动」当零影响证据, 但: stubWriter(196)把落盘方法全换成内存数组, agent 级断言从未碰过路径层; 唯一走真 DiaryWriter 的【29】【34】用 `settings: { diaryFolder: "日记" }` 直接造对象不经 4602 的 Object.assign, pathFormat/attachmentMode 是 undefined, 若实现照写 `renderPath(settings.pathFormat, day)`, moment.format(undefined) 给出含冒号的 ISO 串, fakeVault 只当 key 用照样绿, 线上真 vault create 直接失败; 549/558/809 只用 diaryPath 返回值当 key, 从不与字面路径比较; 桩(44–49)没有 moment, normalizePath 是恒等函数。改法: ① diaryPath/attachmentPath 里 `settings.pathFormat || DEFAULT_SETTINGS.pathFormat`、`attachmentMode || "diary"` 兜底(与 3179 `diaryFolder || "日记"` 同款), 不押在 Object.assign 上; ② moment 桩(实现见 A5)放 stub 里或 __internals 注入都行, 但要在【29】之前生效; ③ 新增黄金文件回归: 用 BOUND_DATA 那种 0.3.1 形状的 data.json 起真插件+fakeVault, 跑一天脚本(文字、两行含 `## ` 的文字、语音原声块、图片、晚安、撤回、跨天封存), diaryPath/attachmentPath/attachmentPathNamed 的返回值与整个文件内容与从 0.3.1 实跑抓下来的**硬编码字面字符串**逐字节比较; ④ 发版前在生产库 用 0.3.1 的 data.json 原样启动, 当天文件 diff 为空。

**A10 · 「从每日笔记设置导入」按核心插件真实取值处理: 根目录、空格式、不带 .md 的模板路径、启用判断 [DN-5, ENG-10] — §2 导入按钮 / §4.3 模板 / §3 diaryPath**
核心每日笔记的 options: `folder` 空 = 库根目录(从没改过设置的最大人群), `format` 空 = `YYYY-MM-DD`, `template` 存的是不带 .md 的链接式路径、核心用 `metadataCache.getFirstLinkpathDest(normalizePath(t), "")` 解析。草案一个都没处理: diaryPath/attachmentPath/attachmentPathNamed(3179/3185/3193)与设置页 onChange(4463)都是 `|| "日记"`, 根目录根本表达不了, 导入后静默写进「日记/2026-08-29.md」, 用户打开根目录的每日笔记什么都看不到; format 空直接填进 pathFormat 会被校验拒掉(用户看到自己没打过的值报错); 模板路径用 getFileByPath 找不到 → 按 §4.3「没有模板」建文件 + console.warn → 微信先到的每一天都丢模板, 正是 §4.3 自己要避免的事; `getPluginById` 关着时也返回对象, 「没启用」要看 `.enabled`。改法: folder 空 → diaryFolder 存显式 `"/"`, 三个路径函数里 `"/"` 视为根目录不拼前缀, 现有 `|| "日记"` 兜底一处不改(独立模式老用户零影响), 设置页 desc 写「填 `/` = 库根目录」, 草案 §2 明写这与 D4「默认 日记」不冲突(只是默认值); format 空 → `YYYY-MM-DD`; template 用 getFirstLinkpathDest(4929 语音气泡已在用同一接口)解析成 TFile 存 `.path`, 再兜一次 `t + ".md"`, 两者都空时导入当场 Notice「模板文件没找到, 请手填」; 每次建文件读模板失败不能只 console.warn——微信回执照说「记下来啦」(内容确实记了), 但 Obsidian 侧 Notice + 设置页 templatePath 的 desc 标红「上次没找到模板文件」。「没启用」Notice 后加一句「用 Periodic Notes 的把它的日期格式抄到上面」。renderTemplate 的占位符集合(草案说「就这三个」, 一个驳斥者查核心源码说对, 另一个说 daily-notes-interface 还有 yesterday/tomorrow)动手前在生产库 开核心插件建一篇逐个对拍, 结果回填 §4.3, 核心不支持的不做; 正则用非贪婪 `(?::([^}]*))?` 让 `{{time:HH:mm}}` 的冒号只切第一个。bindtest 的 makeApp 补 metadataCache 与 internalPlugins 桩。

**A11 · 附件路径函数保持同步, 只新增一个 async 解析层; 删掉「撞名重试只在前两种模式做」 [STD-4] — §3 / §6**

**A14 · 共用模式 + obsidian 附件模式: 算附件路径前先保证当日文件存在 [DN-6, ENG-6] — §3 obsidian 分支**

## B. 需要谷雨拍板(产品选择题)

**B1 · 开关关着、路径却指向用户每日笔记时, 独立模式会把用户的每日笔记当成自己的文件 [STD-9②] — §2 开关 / §4.2 / 导入按钮**
场景: 用户按草案用「从每日笔记设置导入」把 diaryFolder/pathFormat 填成每日笔记的位置, 试完开关又关掉(试一次新功能再关掉是最常见的动作); 或者 Roy 第一条留言的原始诉求——只要路径可配、开关不开。此时独立模式对整个文件操作: 新消息不套节直接追加(用户文件里多出 frontmatter 之外的段头), countMessages 把用户每个 `\n\n` 块数成段, 「撤回」按 3385 删掉用户每日笔记的最后一个非段头块——撤光我们的内容后, 下一次「撤回」删的是 `## 微信随手记` 行(isMessageBlock 不排除 `## `), 再下一次删的就是用户自己的最后一段。这是"动用户自己的内容", 草案「开关关着时 §4 的代码一行都不进」把这个漏洞盖住了。三个选项:
- (a) **独立模式加"外来文件"护栏**: 文件存在、非空、没有 `source: wechat-diary` frontmatter(020/019 建的文件都有, 空文件补全的也有, 所以这是可靠的"我们建的"标记)→ 写入照常追加(内容优先记下), 但 undoLastBlock 拒绝删并回执「这个文件不是插件建的, 撤不了, 请到 Obsidian 里手动删」, countDay 只数我们段头之后的块。对默认布局的老用户永远不触发(他们的文件都有 frontmatter), 零影响成立。
- (b) 只在设置页拦: 关开关或保存 pathFormat 时用今天的渲染路径探测, 命中不是我们建的文件就弹确认「路径仍指向你的每日笔记, 关掉后插件会把它当自己的文件, 撤回会删这个文件的最后一段; 要改回默认路径吗」, 提供「改回默认」按钮(导入按钮记住导入前的值)。不改写入逻辑, 但挡不住"明天核心插件再建一篇"。
- (c) 两者都做。
**推荐 (c)**, 至少要 (a): (b) 是提示, (a) 才是护栏; 撤回删用户段落是这一轮唯一一条"开关关着也会动用户内容"的路径, 只靠 README 说不过去。

**B2 · 逻辑日 4 点 vs 每日笔记零点: 要不要给 dayStartHour 一个设置 UI [DN-8 UI 半] — §4.4**
逻辑日 4 点当初就是为夜猫子设的, "零点后发消息"是这群人的日常; 共用模式下这些内容进的是昨天那份每日笔记, 用户早上打开日历日的今天, 节里是空的。§4.4 只靠 README + 手改 data.json(2370 注释自认无 UI), 非开发者用户等于没有这条路。选项:
- (a) 开关开着时设置页露出「一天从几点开始」(0–12, 默认仍 4), desc 写「用每日笔记的建议填 0; 每日提醒的最晚时间也跟着变」(现 desc 4501 写死"最晚 03:59", 要改成动态)。

**推荐 (a)**: `_dayStartHour` 是全局的(reminderDue 2546、isNightNow 2416、晚安池都用它), (b) 会让用户打开开关的瞬间提醒窗口悄悄变了, 不直白; (c) 对共用模式人群等于没给路。契约 v1.2 拍的是逻辑日与 dayStartHour 可配, "无 UI"是当时状态不是禁令, (a) 不碰不开开关的用户。A15 的带日期回执无论选哪个都做。

**B3 · pathFormat/attachmentFolder 校验的交互形态 [STD-8, ENG-5 后半] — §2 校验规则 / 设置页 4463–4490**
草案 §2 同一句里既要「不合法 → Notice」又要「半截输入中间态不报错」, 但格式串没有像提醒时间 `HH:MM` 那样的形状可判(`YYYY/MM/YYYY-MM-D` 与 `YYYY/MD` 语法上都"完整"): 照现有「日记文件夹」每键 onChange 落地, 用户从空打到 `YYYY/MM/YYYY-MM-DD` 的十几个中间态几乎全过不了校验, 每键一条 Notice——所有改格式的用户第一次输入必撞。不落盘这点没有争议(错误格式一旦存进 data.json 后续写入就落到错位/撞车的文件); 争的是形态, 谷雨对 #14 说过设置 UI 形态要她再聊, 所以提给她:
- (a) 输入框下方一行实时预览「今天会写到: 日记/2026/08/2026-08-29.md」, 不合法时预览行变红写原因(「英文字母会被当成日期代码, 请用方括号括起来」/「这个格式两天会写进同一个文件, 没有保存」), 不弹 Notice, 只在合法时落盘, 200–600ms 去抖。Obsidian 每日笔记设置页同款做法, A5 的乱码问题也在用户眼前现形。
- (b) 校验与落盘改到 blur/回车后, 不合法时 Notice 一次并回退到上一个合法值。
- (c) 自定义附件位置拆成「附件文件夹(不渲染, 复用现有输入即搜索组件)」+「子路径格式(可空)」, 用户的 `Assets` 根本不进 moment; 与 (a)/(b) 可叠加。
**推荐 (a)**, (c) 可作为加项: 预览是唯一能让用户在保存前看见结果的形态, 与"失败必须响亮"和"直白"都对得上; (b) 回退时半截输入无声消失。
